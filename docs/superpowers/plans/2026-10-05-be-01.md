# BE-01 implementation plan

> Execution: use superpowers:executing-plans and test-driven-development inline.

**Goal:** Bootstrap `backend/` with uv and satisfy the first ticket's API and development-environment requirements.

**Architecture:** An installable `src/fluke_backend` package exposes an application factory. Settings load at factory invocation, never at module import. PostgreSQL is a separate development service; database lifecycle starts in BE-02.

**Tech stack:** Python 3.11, uv, FastAPI, Pydantic Settings, Uvicorn, pytest, Ruff; Docker Compose with PostgreSQL 17 (confirmed by user).

**Spec:** [BE-01](../../TICKETS.md) and [backend architecture](../../BACKEND.md).

## Constraints and decisions

- Only implement BE-01. No accounts, database engine, tables, migrations, or training yet.
- Require `FLUKE_DATABASE_URL` at startup; validate PostgreSQL syntax without connecting. Hide credential-bearing inputs in errors and representations.
- Reserve an optional `runner` extra; its pinned FLUKE dependencies arrive in BE-14. Default installs contain neither FLUKE nor PyTorch.
- Keep the current workspace: it has no Git repository, so worktrees and commits do not apply.
- Use project-local uv cache and managed Python during this sandboxed session.

## Review focus

- Missing or malformed database configuration must stop startup clearly.
- Credential-bearing invalid values must not appear in startup error text.
- Environment values must override the local example-derived `.env` file.
- Import and liveness must not connect to PostgreSQL or load training libraries.
- A clean, non-editable locked install must expose the same HTTP contract.
